adaptive-lb

An HTTP load balancer written from raw sockets and threads in Python, with health checks, circuit breakers and retries, comparing four routing strategies (round robin, least connections, an ML latency model and a multi-armed bandit) across controlled, repeated experiments. Every number below was measured.

  • Concurrency: a listener thread accepts TCP connections into a bounded queue; a fixed pool of worker threads serves them (producer-consumer with condition variables), so overload costs latency, not unbounded threads.
  • Reliability: active health checks (TCP + GET /health), a circuit breaker per backend fed by real requests, retries of idempotent requests on another backend with exponential backoff, and token-bucket rate limiting.
  • Strategies: round robin rotates; least connections picks the fewest requests in flight; ML latency predicts each backend's response time with a linear model (in-flight requests, CPU, memory, recent latency) trained offline on earlier runs; the bandit is epsilon-greedy over each backend's last 50 latencies. Both ML strategies fall back to least connections when they can't decide within 2 ms.
  • Logging: every request goes to PostgreSQL through one writer thread in batched transactions; results are computed in SQL.

Methodology

  • Every run starts fresh backend processes and a fresh load balancer, so no state carries over.
  • Load is open-loop: requests are sent on a Poisson schedule whether or not earlier ones have answered, so a slow server shows up as latency instead of quietly reducing the load.
  • Every strategy gets the same random seeds, so it sees the identical sequence of arrivals. The seeds differ from those of the runs the ML model was trained on.
  • Each cell is reported as the mean ± standard deviation over the runs, with the min–max range. A "winner" is only named when its latency (at the chosen percentile) beats the others by more than that spread; otherwise the card says it's a tie.
  • p50, p95 and p99 are computed the same way everywhere: Postgres percentile_cont (linear interpolation) over a run's successful requests, all three from one sort.
  • Retries were off during the experiments, so errors show what the routing did. Each run's request log was cross-checked against the load generator's own count.
  • Limitations: one laptop, synthetic backends with artificial delays, and a single (not replicated) load balancer. The model was trained on earlier runs of the same scenarios, so this is its best case.
