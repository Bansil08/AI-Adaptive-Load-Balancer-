# Concepts map

Every feature in this project, the file that implements it, and the CS concept it demonstrates.

| Feature | File | Subject | Concept | Interview one-liner |
|---------|------|---------|---------|---------------------|
| Normalised schema | `db/schema.sql` | DBMS | Third normal form (3NF) | Every non-key column depends only on its table's key, so facts like a server's address are stored once and can't drift out of sync. |
| Foreign keys + `ON DELETE` rules | `db/schema.sql` | DBMS | Referential integrity | FKs stop orphan rows; servers use RESTRICT + soft delete to keep history, run results CASCADE with their run. |
| CHECK / NOT NULL constraints | `db/schema.sql` | DBMS | Domain integrity | The database itself rejects impossible data (CPU 150%, check_type 'udp'), not just the application. |
| Atomic schema migration | `scripts/init_db.py` | DBMS | Transactions (transactional DDL) | Postgres runs CREATE TABLE inside a transaction, so the schema is applied entirely or not at all. |
| Stored run aggregates | `db/schema.sql` (`run_results`) | DBMS / System design | Controlled denormalisation | p95 etc. are derivable from `requests` but cached so plots are cheap and results outlive the 7-day retention job. |
| Sockets API | `lb/server.py`, `lb/proxy.py` | CN / OS | socket, bind, listen, accept, connect, send, recv, shutdown, close | Server: socket→bind→listen→accept gives one new socket per client; client side: `create_connection` does socket+connect (TCP 3-way handshake). Every socket is a file descriptor. |
| Listening socket | `lb/server.py` | CN | socket → bind → listen → accept | The kernel completes the TCP 3-way handshake and queues up to `backlog` connections until `accept()` hands us one. |
| `SO_REUSEADDR` | `lb/server.py` | CN / OS | TIME_WAIT | Lets the LB restart immediately; otherwise old connections in TIME_WAIT make `bind()` fail with "address already in use". |
| Thread-per-connection (baseline) | `lb/server.py` (`--thread-per-connection`) | OS | Threads, concurrency | Each accepted socket gets its own thread so one slow backend doesn't block other clients; simple, but the thread count is unbounded. Kept as the benchmark baseline. |
| Producer-consumer | `lb/server.py`, `lb/bounded_queue.py` | OS | Bounded buffer problem | The listener (producer) puts accepted sockets into a bounded queue; a fixed pool of workers (consumers) takes them out, so accepting and serving are decoupled. |
| Hand-written bounded queue | `lb/bounded_queue.py` | OS | Mutex + condition variables | One lock, two conditions (`not_full`, `not_empty`); `wait()` releases the lock and sleeps atomically, so no busy-waiting and no lost wakeups. Re-check in a `while` loop because another thread may take the slot first (and wakeups can be spurious). |
| Backpressure | `lb/server.py` (`_enqueue`) | OS / System design | Flow control | When the queue is full the listener stops calling `accept()`; new connections wait in the kernel's listen backlog, and beyond that the kernel drops SYNs, so overload costs latency, not unbounded memory or threads. |
| Fixed thread pool | `lb/server.py` | OS | Thread pool vs thread-per-connection | N workers are created once; thread count (and stack memory) stays constant no matter how many clients connect. A worker catches unexpected errors so a bug can't permanently shrink the pool. |
| Pool vs thread-per-connection (measured) | `experiments/benchmark_concurrency.py`, `experiments/results/concurrency_benchmark.md` | OS / System design | Bounded vs unbounded concurrency | 50 ms backends, 200 clients: 32-worker pool 564 req/s (p95 377 ms, capped by 32 / 0.057 s), 256-worker pool 3426 req/s at 257 threads, thread-per-connection 3378 req/s at 201 threads. At 500 clients thread-per-connection was ~9% faster (4652 vs 4276 req/s) but used 437 threads vs a fixed 257; the pool's win is a hard cap on threads, not speed. |
| Ephemeral port exhaustion | `experiments/benchmark_concurrency.py` | CN / OS | TIME_WAIT, ephemeral ports | A new TCP connection per request leaves each closed one in TIME_WAIT for 2·MSL (30 s on macOS) holding one of ~16k ephemeral ports; at ~3.4k req/s the benchmark hit `EADDRNOTAVAIL` until it waited for TIME_WAIT to clear between runs. Connection pooling (Phase 3) is the real fix. |
| Whole-request deadline (slowloris) | `lb/http_parser.py` (`SocketReader`), `lb/proxy.py` | OS / Security | Resource exhaustion in a fixed pool | A socket timeout only limits the gap between two `recv()`s, so a client dripping one byte at a time held a worker forever (measured 18.7 s and counting at a 1 s timeout). Now the whole request must arrive within `client_timeout` (3 s). Known limit: each slow client still holds a worker for up to that long (+2 s lingering close), so ~32 slow clients can stall a 32-worker pool for a few seconds; the real fix is `select`/`epoll`, which this project deliberately leaves out. |
| Readers-writers lock | `lb/rwlock.py` | OS | Readers-writers problem | Many readers share the lock, a writer gets it alone; built from one condition variable and three counters. |
| Writer preference | `lb/rwlock.py` | OS | Starvation | A waiting writer blocks *new* readers; otherwise overlapping readers could keep it out forever (writer starvation). The trade-off: a steady stream of writers can starve readers instead. |
| Shared server stats | `lb/stats.py` | OS / System design | Shared state, consistent snapshots | Active connections, total requests and an EWMA latency per backend; readers get an immutable copy taken under the read lock, so all backends are seen at one instant. |
| Recent-latency average (EWMA) | `lb/stats.py` | System design | Exponentially weighted moving average | `avg = 0.2·sample + 0.8·avg` needs O(1) memory and forgets old samples, so it tracks a backend that slows down (a plain mean wouldn't). |
| Deadlock prevention | `lb/server.py` (docstring), below | OS | Lock ordering (breaks circular wait) | No code path holds two locks at once; if one ever must, it takes them in one documented global order, which makes a cycle of waiting threads impossible. |
| Graceful shutdown | `lb/server.py` (`_drain`) | OS / System design | Draining | On SIGINT/SIGTERM: close the listening socket (new connects refused), let workers finish in-flight and already-queued requests, give up after `shutdown_timeout`. |
| Signal handling | `lb/server.py` (`main`) | OS | Signals, async-signal safety | The handler only sets a flag: it runs on the main thread between bytecodes, so taking a lock (even logging's) could deadlock against the code it interrupted. A second signal gets the default action and kills immediately. |
| Surviving fd / thread exhaustion | `lb/server.py` | OS | File descriptor limits (`ulimit -n`), EMFILE | Each connection costs 2 fds; when `accept()` hits "Too many open files" we log, back off and continue, so one client fails instead of the whole LB crashing (measured: 100 requests at a 64-fd limit went from 100 failed + crash to 70 OK + LB up). |
| TCP byte stream | `lb/http_parser.py` (`SocketReader`) | CN | Stream vs message delivery | TCP guarantees bytes arrive in order, not that one send() equals one recv(); so we read until `\r\n\r\n`, then exactly Content-Length bytes, keeping leftovers buffered. |
| Buffered stream reader | `lb/http_parser.py` (`SocketReader`) | CN | TCP is a byte stream | `recv()` can return half a message or two messages, so we buffer and frame by `\r\n\r\n` + `Content-Length`. |
| HTTP message format | `lb/http_parser.py` | CN | Start line, headers, blank line, body | `GET /path HTTP/1.1` or `HTTP/1.1 200 OK`, then `Name: value` lines, a blank line (CRLF CRLF), then a body whose length Content-Length gives. |
| Hand-written HTTP/1.1 parser | `lb/http_parser.py` | CN | Application-layer protocol framing | Request line, headers and body are parsed by hand; HEAD/204/304 responses have no body even if Content-Length says otherwise. |
| Strict parsing | `lb/http_parser.py` | CN / Security | HTTP request smuggling | We reject conflicting Content-Length, TE+CL, folded headers and spaces before the colon, because front and back servers could disagree on where a request ends. |
| Input validation with `fullmatch` | `lb/http_parser.py` | Security | Injection / bare-LF tricks | `re.match(r"^[0-9]+$")` accepts `"5\n"` because `$` matches before a trailing newline; `fullmatch` doesn't. Paths must be visible ASCII, so no log-injection escape codes or NUL bytes. |
| Size limits + timeouts | `lb/config.py`, `lb/proxy.py` | OS / Security | Resource exhaustion | Header (431) and body (413) caps plus socket timeouts stop a client from pinning memory or a thread forever. |
| `Expect: 100-continue` | `lb/proxy.py` | CN | Protocol handshake | The client asks before sending a large body; we answer `100 Continue` and only then read it. |
| Hop-by-hop header stripping | `lb/proxy.py` | CN | Proxy semantics (RFC 9110) | `Connection`, `Keep-Alive` etc. describe one TCP link, so a proxy drops them instead of forwarding them. |
| Reverse proxy | `lb/proxy.py` | CN / System design | Reverse vs forward proxy | Clients talk to the LB as if it were the server; it picks a backend, opens its own TCP connection, relays the response, and hides backend addresses from clients. |
| `X-Forwarded-For` | `lb/proxy.py` | CN | Reverse proxy | The backend only sees the LB's IP, so we append the real client IP to the header chain. |
| 502 vs 504 | `lb/proxy.py`, `lb.toml` | CN | Gateway error semantics | 502 Bad Gateway = backend refused, reset, or sent garbage; 504 Gateway Timeout = backend didn't connect/answer within the configured timeout; 503 = no backend at all. |
| Gateway error mapping | `lb/proxy.py` | CN / System design | 502 / 503 / 504 | Refused or invalid backend → 502, no backend → 503, backend too slow → 504, so failures are explicit, not hangs. |
| Lingering close | `lb/proxy.py` (`close_gracefully`) | CN | FIN vs RST | `close()` with unread bytes in the receive buffer sends RST, which can destroy our response; `shutdown(SHUT_WR)` + drain + close lets the client read it (measured: a 413 was lost 10/10 times before). |
| Config file | `lb.toml`, `lb/config.py` | System design | Configuration vs code | Backends, port, strategy and timeouts live in TOML (stdlib `tomllib`), validated on load, so changing them needs no code change. |
| Backends in Docker Compose | `docker-compose.yml` | OS / System design | Containers, PID 1 signal handling | `init: true` adds a tiny init as PID 1 to forward SIGTERM; PID 1 ignores signals without handlers, so stop would otherwise wait 10 s for SIGKILL (measured 0.24 s with it). |
| Strategy interface | `lb/strategies/base.py`, `lb/router.py` | System design | Strategy pattern | Proxy code only calls `choose()`, so new routing algorithms plug in without touching forwarding. |
| Round robin with a lock | `lb/strategies/round_robin.py` | OS | Race condition, mutual exclusion | Counter read-increment-write is made atomic with a `Lock`; a test with 8 threads checks the split is exactly even. |
| Test backend | `backend/app.py` | System design | Simulated latency | `sleep()` models I/O-bound latency per backend; `/health` stays instant because it measures liveness, not speed. |
| Active health checks | `lb/health.py` | CN / System design | TCP vs HTTP liveness | A background thread probes every backend: TCP connect (is something listening?) then `GET /health` = 200 within a timeout (is it actually answering? A hung process's kernel still completes handshakes). |
| Hysteresis (K down / M up) | `lb/health.py` (`HealthState`) | System design | Debouncing / flap prevention | Down only after K consecutive failed probes, back up only after M consecutive passes, so one dropped packet doesn't bounce a backend in and out of rotation. |
| Circuit breaker | `lb/circuit_breaker.py` | System design | Fail fast, CLOSED / OPEN / HALF_OPEN | N consecutive real-request failures → OPEN: stop sending for a cooldown (fail fast, let it recover) → HALF_OPEN: a few trial requests → CLOSED if they all succeed, OPEN again if one fails. |
| State pattern | `lb/circuit_breaker.py` | System design | Design patterns | Each breaker state is a class with the same methods (`try_acquire`, `on_success`, `on_failure`); the breaker delegates to its current state, so each state's rules live in one place instead of an if/elif on a state string. |
| Health checks vs breaker | `lb/health.py`, `lb/circuit_breaker.py` | System design | Active vs passive failure detection | Health checks are active (synthetic probes on a timer; detect a dead backend with no traffic and detect recovery); the breaker is passive (real outcomes; reacts within a few requests and catches failures `/health` can't see, like a broken endpoint or overload). |
| Lazy timers | `lb/circuit_breaker.py`, `lb/rate_limiter.py` | OS / System design | Compute on access instead of a timer thread | OPEN → HALF_OPEN happens on the first request after the cooldown, and buckets refill by `elapsed * rate` when checked; no background threads, no timers to cancel. |
| Router leases + drain | `lb/router.py` (`acquire` / `release` / `drain_and_remove`) | OS | Condition variable, safe removal | `draining` is set under the same lock `acquire()` checks, so no new request can start on that backend; the remover then waits on a condition variable until the in-flight count reaches 0 (or a timeout). The `Lease` holds the backend's state object, not its address: a bug found in review had a request left over from a forced removal decrement a *re-added* backend's count to -1. |
| Copy-on-write backend list | `lb/router.py` | OS | Immutable snapshots | Add/remove builds a new tuple; a thread iterating the old tuple is unaffected, so readers (health checker, strategies) don't need the lock while iterating. |
| UDP heartbeats | `backend/agent.py`, `lb/heartbeat.py` | CN | UDP vs TCP | Heartbeats are "latest value" reports every second: a lost one is replaced by the next, so UDP's no-handshake, no-retransmit, connectionless delivery fits; proxied requests need every byte exactly once and in order, so they use TCP. |
| Sequence numbers over UDP | `lb/heartbeat.py` | CN | Reordering / duplicates | UDP can reorder and duplicate datagrams, so each carries `(agent start time, seq)`; older or repeated ones are dropped. A restarted agent has a newer start time, so its seq may restart at 0. |
| `recvfrom` keeps boundaries | `lb/heartbeat.py` | CN | Datagram vs stream sockets | `SOCK_DGRAM`: no `listen`/`accept`, and one `recvfrom()` returns exactly one datagram, unlike TCP where one `recv()` may hold half or two messages. |
| Per-process CPU/memory | `backend/agent.py` | OS | Process accounting (psutil) | All dev backends share one machine, so system-wide CPU would be identical for each; the agent reports its own process's CPU (divided by core count to get 0–100) and memory. |
| Spoofable UDP | `lb/heartbeat.py` | Security | Unauthenticated datagrams | Anyone can forge a UDP source, so the listener binds to loopback and ignores unknown backends; a real system would HMAC-sign heartbeats. |
| Connection pooling | `lb/connection_pool.py`, `lb/proxy.py` | CN / OS | HTTP/1.1 keep-alive, 3-way handshake, TIME_WAIT | Reusing a persistent backend connection skips the SYN / SYN-ACK / ACK round trip, the socket + fd setup, the backend's thread-per-connection start, and the TIME_WAIT socket each close leaves behind. Measured (loopback, 0 ms backends, `experiments/results/pooling_benchmark.md`): 3696 → 4782 req/s at 1 client (+29%), 5514 → 7273 at 8 (+32%), 5379 → 7261 at 32 (+35%, p95 7.1 → 5.1 ms); backend connections per 1000 requests 1000 → 0.2–1.4; TIME_WAIT sockets on backend ports ~14k → ~60. Re-measured in Phase 4 after the TCP_NODELAY fix below (before it: +34% / +23% / +28%). One loopback connect costs ~31 µs median; on a real network add one full RTT per handshake. |
| Stale pooled connections | `lb/connection_pool.py` (`peer_closed`) | CN | FIN detection with `MSG_PEEK` | Before reusing an idle connection, a non-blocking `recv(1, MSG_PEEK)`: `b""` means the backend already sent FIN (closed it), so it is discarded; LIFO reuse + an idle timeout keep old ones from piling up. The peek can still race with a close that happens right after it, so if a reused connection fails before a single response byte arrives, a GET/HEAD is resent once on a fresh connection to the same backend (a POST is not: the backend may have processed it). |
| Nagle's algorithm vs delayed ACK | `backend/app.py`, `lb/connection_pool.py` | CN | TCP_NODELAY | Nagle holds a small write until the previous one is ACKed; the receiver delays ACKs (up to ~40 ms) hoping to piggyback them. `http.server` writes headers and body separately, so on a long-lived pooled connection every response stalled (found in Phase 4: 71 ms vs 25 ms through the LB to the Docker backends; a fresh connection hid it because Linux ACKs a new connection's first packets at once). Fix: `TCP_NODELAY` on both sides, as nginx, Go and Node do by default. |
| Message framing for keep-alive | `lb/http_parser.py` (`read_chunked`, `framed_by_close`) | CN | Content-Length vs chunked vs close-delimited | On a reused connection the LB must know exactly where a response ends, so chunked bodies are parsed (sizes in hex, `0` ends) and close-delimited ones mark the connection unreusable. |
| Idempotent-only retries | `lb/proxy.py` | CN / System design | Idempotency (RFC 9110) | GET/HEAD are retried on a different backend when there was no usable answer; POST never is, because the backend may already have processed it (double charge). An actual HTTP response, even 500, is passed through, not retried. |
| Exponential backoff | `lb/proxy.py` (`backoff_delay`) | System design | Avoiding retry storms | Waits base, 2·base, 4·base… (capped) between attempts, so a struggling cluster isn't hammered by instant retries. Adding random jitter is the usual next step to de-synchronise clients. |
| Token bucket | `lb/rate_limiter.py` | System design / OS | Rate limiting, atomic check-and-decrement | Bucket of `burst` tokens refilled at `rate`/s: allows short bursts but caps the long-run rate; one lock makes "refill, check, take" atomic so two threads can't spend the last token. At most `max_clients` buckets are kept in an LRU `OrderedDict`; a new IP beyond that evicts the least recently seen one in O(1) (a review found the first version only evicted full buckets, so memory was not actually bounded). |
| 429 + Retry-After | `lb/proxy.py` | CN | HTTP semantics | An empty bucket gets `429 Too Many Requests` with `Retry-After: <seconds>` computed from the bucket, so well-behaved clients know when to come back. |
| Admin API on its own port | `lb/admin.py` | System design / Security | Control plane vs data plane | Management traffic is separate from client traffic and bound to loopback (no auth). Each admin connection gets its own thread because a DELETE blocks while draining. |
| Sticky sessions | `lb/router.py` (`sticky_choice`) | System design | Rendezvous (HRW) hashing | Each client IP scores every backend with a hash and picks the highest, so the same IP gets the same backend, and removing one backend moves only its clients (`hash % n` would move almost all). SHA-256, not crc32: crc32 is linear, and measured 50% of 600 clients on one of three backends. |
| Failover (measured) | `experiments/demo_failover.py`, `experiments/results/failover_demo.md` | System design | Health checks + breaker + retries together | Backend SIGKILLed under ~160 req/s: with retries off, 3 of 3156 requests failed, all in the first second (breaker opened after 3 failures, health checks marked it DOWN ~1 s later); with retries on, 0 errors. After restart it served traffic again within ~1 s (2 passed probes, half-open trials, closed). |
| Single DB writer thread | `lb/db_writer.py` | OS / DBMS | Producer-consumer, decoupling I/O | Workers only `put()` a record onto Phase 2's `BoundedQueue` (non-blocking, dropped + counted when full); one thread owns the only connection and does all writes, so a slow or dead database never slows a client. |
| Batched transactions | `lb/db_writer.py` | DBMS | Transactions, commit cost | A batch is written when it has N records or T ms after its first record, as ONE transaction: one round trip and one WAL fsync for ~200 rows instead of 200. Measured (`experiments/results/db_benchmark.md`): one INSERT + COMMIT per row 3,060 rows/s; one transaction but a round trip per row 5,245; `executemany` batches of 10 / 50 / 200 / 1000: 10,087 / 25,514 / 52,512 / 60,800 rows/s. Batch of 200 = **17×** per-row commits; the real writer end to end does 47,209 rows/s, several times what the LB can serve. |
| ACID in the writer | `lb/db_writer.py` | DBMS | Atomicity, consistency, isolation, durability | Atomic: a batch commits entirely or not at all (a test checks all 300 rows share one `xmin`, the inserting transaction id). Consistent: CHECK/FK constraints reject bad rows. Isolated: readers never see half a batch. Durable: COMMIT returns after the WAL is flushed (`synchronous_commit = on`). |
| Rollback + SAVEPOINT salvage | `lb/db_writer.py` (`_write_rows_individually`) | DBMS | Savepoints / nested transactions | One bad row aborts the whole transaction, so the batch is rolled back, then retried row by row, each inside a SAVEPOINT (`with conn.transaction()` nested): a failing row rolls back to its savepoint only, the good rows commit, the thread lives on. A test proves no duplicates (the rollback really happened). |
| Transient vs permanent errors | `lb/db_writer.py` | DBMS / System design | Retry policy, at-least-once delivery | A lost connection is retried with backoff (the batch is still in memory, nothing lost); a data error is not retried (it would fail forever); a missing schema (`UndefinedTable`) is logged once a minute, not as a traceback per batch. If the connection dies after COMMIT but before its reply, the retry duplicates the batch: "at least once", fine for logs. |
| Surviving a database outage (measured) | `lb/db_writer.py` | System design | Buffering, graceful degradation | Postgres stopped for 6 s under ~1,000 req/s: clients saw no errors and no slowdown (median 7.6–7.9 ms throughout), the queue peaked at 7,483 records, one reconnect, and all 20,010 requests reached the table. Outage tolerated without loss ≈ `queue_size` ÷ request rate (10,000 ≈ 10 s here); beyond that records are dropped and counted, never blocking a client. |
| Server ids before the batch | `lb/db_writer.py` (`_resolve_servers`) | DBMS | Upsert (`INSERT … ON CONFLICT … RETURNING`) | New backends get their `servers` row in a separate, already-committed transaction, so a batch that later rolls back can't leave the writer caching an id that doesn't exist. `DO UPDATE` (not `DO NOTHING`) so `RETURNING` gives the id on conflict too. |
| Event time, not write time | `lb/db_writer.py`, `lb/proxy.py` | DBMS / System design | Timestamps, what a latency measures | Each record carries the time the request arrived; the batch may be written up to T ms later, which must not shift the data. `response_time_ms` starts once the whole request has been received, so a slow client upload is not blamed on the backend (a review found a 10 ms backend logged at 1,516 ms behind a 1.5 s upload). |
| Persisted health checks + heartbeats | `lb/health.py`, `lb/heartbeat.py` | DBMS | Time-series tables | Each probe is two `health_checks` rows (`tcp`, `http`, own latency; NULL on timeout); each heartbeat is a `server_metrics` row; health transitions and admin removal update `servers.status` (`removed` is a soft delete so history keeps valid FKs). |
| Composite indexes | `db/schema.sql` | DBMS | B-tree index, column order | `(server_id, received_at)`: equality column first, range column second, so "server X, last 15 minutes" is one contiguous slice of the index. Postgres does not index foreign keys automatically. Measured on 1.2M requests / 2.07M heartbeats: dashboard views 19–34 ms → 0.43–0.74 ms (26–78×); training-export sample 10.8 s → 0.27 ms; whole export of 1.19M rows 2.8 s. Cost: 36 MB + 62 MB of index, built in ~0.5 s each, maintained on every insert (the insert numbers above already include both indexes). |
| EXPLAIN ANALYZE | `experiments/benchmark_db.py`, `experiments/results/db_benchmark.md` | DBMS | Query plans | Shows the plan the planner chose *and* what actually happened (rows, time, buffers read). Before: Seq Scan over every row + filter; after: Index Scan reading only matching rows. See "Indexes: before and after" below. |
| Index-friendly query shape | `db/queries.sql` | DBMS | Join order, nested loop | Views start from `servers` (3 rows) and join `requests ON server_id = s.id AND received_at >= …`, so the planner can run one index range scan per server (nested loop) instead of scanning 1.2M rows. |
| Views | `db/queries.sql` | DBMS | Views (virtual tables) | A stored, named SELECT run on every read (not cached; that would be a materialized view). The dashboard and ML code use the names, so the SQL lives in one place. |
| `LEFT JOIN … ON` vs `WHERE` | `db/queries.sql` | DBMS | Outer joins | Putting the time filter in `ON` keeps servers with no recent traffic (0 requests); in `WHERE` it would silently turn the outer join into an inner one and hide them. |
| `LATERAL` join ("latest row before") | `db/queries.sql` (`training_data`) | DBMS | Correlated subquery, top-1 per row | For each request, `LATERAL (… WHERE server_id = r.server_id AND recorded_at <= r.received_at ORDER BY recorded_at DESC LIMIT 1)` picks the newest earlier heartbeat. With the index that is one probe per request; without, a full scan per request. |
| Percentiles in SQL | `db/queries.sql` | DBMS / Statistics | Ordered-set aggregates | `percentile_cont(0.95) WITHIN GROUP (ORDER BY response_time_ms)` sorts each group and interpolates; a test checks 1..20 ms gives p95 = 19.05. `FILTER (WHERE …)` counts errors inside the same aggregate pass. |
| Batched retention | `scripts/retention.py` | DBMS | Long transactions, locking, MVCC bloat | Deleting 7-day-old rows 5000 per transaction keeps locks short, WAL small and lets autovacuum reclaim space; one huge DELETE holds every row lock to the end, bloats the table and loses everything if it fails. Measured on 150k requests (one day): batches of 5000 median 12–14 ms per transaction on a quiet database (67 ms right after the 1.2M-row bulk load, while Postgres was checkpointing it), longest 88–122 ms; one DELETE held all 150k rows for 191 ms and grows with the delete size, a batch does not. Batching is slower in total (1.35 s vs 0.19 s): it trades throughput for short locks. A review of the first version found each batch rescanning rows earlier batches had deleted (65 → 213 ms per batch, worse than one DELETE); keyset pagination (`id > last_deleted`) fixed it. |
| Least connections | `lb/strategies/least_connections.py` | System design / OS | Adaptive load balancing, shared-state reads | Send each request to the backend with the fewest requests in flight, read from the live stats under the readers-writers lock (the read-heavy path that lock was built for). Ties rotate, so idle backends aren't all ranked "first". |
| Little's law | `lb/strategies/least_connections.py` | System design / Queueing | L = λ·W | Requests in flight = arrival rate × time each spends in the system. A slower backend holds requests longer, so it shows more in flight and least connections sends it less, without ever measuring speed. Limitation: a backend that *fails* fast (refused in ~1 ms) shows few in flight and attracts traffic until health checks / the breaker remove it. |
| p95 vs average | `db/queries.sql`, `experiments/run_experiments.py` | Statistics / System design | Tail latency | The average hides the slow tail: one request in 20 is slower than the p95, and a page that makes 20 calls almost always hits one. Measured (Phase 5, unequal servers): least connections cut the average 87 → 60 ms (−31%) but the p95 only 170 → 166 ms, because it still sends 15% of requests to the 150 ms server, more than 5%, so the 95th percentile is still a slow-server response. In the slowdown run the opposite: average 50 ms but p95 45 ms, because the 300 ms responses were ~4.5% of requests, fewer than 5%, so they raise the average yet sit above the p95. Report both. |
| Open-loop load generator | `experiments/load_generator.py` | System design / Testing | Load testing, coordinated omission | Requests leave on a schedule (Poisson arrivals, seeded) whether or not earlier ones finished, like independent users; latency is timed from the *scheduled* send. A closed loop ("send, wait, send") slows down when the server does, so it sends less load exactly when things go wrong and under-reports latency. A test checks the queueing delay shows up. |
| Capacity and queueing | `backend/app.py` (`--capacity`) | OS / Queueing | Counting semaphore, utilisation | A `BoundedSemaphore(N)` lets N requests work at once; the rest wait, so a backend serves at most N / delay requests per second. Past that, arrivals exceed service and the queue (and latency) grows for as long as the overload lasts. Without it a `sleep()` backend never slows down, and a spike could not be simulated. |

## Deadlock prevention: lock order

Locks in the load balancer:

| Lock | File | Protects |
|------|------|----------|
| `BoundedQueue._lock` (+ its two conditions) | `lb/bounded_queue.py` | the queue's deque and closed flag |
| `LoadBalancer._handlers_lock` | `lb/server.py` | set of live thread-per-connection handlers |
| `Router._lock` (+ its `_lease_ended` condition) | `lb/router.py` | backend list, health / draining flags, in-flight leases |
| `HealthChecker._states_lock` | `lb/health.py` | per-backend probe counters |
| `CircuitBreaker._lock` (one per backend) | `lb/circuit_breaker.py` | the breaker's current state |
| `ServerStats._lock` (`ReadWriteLock`, internally one mutex) | `lb/stats.py` | per-backend counters and latest heartbeat |
| `ConnectionPool._lock` | `lb/connection_pool.py` | idle connection stacks and counters |
| `RateLimiter._lock` | `lb/rate_limiter.py` | the per-IP token buckets |
| `RoundRobinStrategy._lock` | `lb/strategies/round_robin.py` | the round-robin counter |
| `LeastConnectionsStrategy._lock` | `lb/strategies/least_connections.py` | the tie-break counter (taken after the stats snapshot is released) |
| `GuardedStrategy._fallback_lock` | `lb/strategies/guarded.py` | the fallback counter (released before logging and before least connections runs) |
| `EpsilonGreedyStrategy._lock` | `lb/strategies/bandit.py` | per-backend reward windows and the random generator (released before least connections runs for untried arms) |
| `DBWriter._counters_lock` | `lb/db_writer.py` | the writer's counters (its queue is a `BoundedQueue`, first row) |

A deadlock needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, and **circular wait** (thread 1 holds A and waits for B while thread 2 holds B and waits for A). We break circular wait:

1. Today no code path holds two of these locks at the same time (each critical section is a few lines and calls nothing that locks), so hold-and-wait never happens either. Phase 3 keeps this on purpose: `Router.acquire()` reads candidates under the router lock, *releases it*, and only then asks each circuit breaker (its own lock) and the strategy (its own lock); the health checker asks the router for initial health *before* taking its own lock.
2. If a later phase needs two at once, it must take them in the order of the table above (queue → handlers → router → health → breaker → stats → pool → rate limiter → strategy → DB writer counters) and release in reverse. With one global order every thread waits only "downwards", so no cycle can form.
3. Never log, block on I/O, or call user code while holding a lock: `logging` has its own internal lock, and a slow call while holding a lock stalls every other thread that needs it.
4. `ReadWriteLock` is not reentrant: upgrading read → write in the same thread deadlocks with itself, so code takes the write lock from the start when it might write.

## Indexes: before and after (EXPLAIN ANALYZE, 1.2M requests)

Measured by `python -m experiments.benchmark_db` in a throwaway database: 1,200,000 requests and 2,073,603 server_metrics rows over 8 days, 3 servers, PostgreSQL 16 in Docker Desktop with default settings. Each query was run 3× with `EXPLAIN (ANALYZE, BUFFERS)`; times are medians. Full plans: `experiments/results/db_benchmark.md`.

| Query | Without indexes | With indexes | Speed-up |
|---|---:|---:|---:|
| p95 / avg latency per server per minute, last 15 min | 19.51 ms | 0.74 ms | 26× |
| Error rate per server, last 15 min | 34.48 ms | 0.44 ms | 78× |
| Request count per server, last 15 min | 19.07 ms | 0.43 ms | 44× |
| Training export, latest 100 requests (LATERAL join) | 10,822 ms | 0.27 ms | 40,083× |

**Dashboard: latency per server per minute.** Without the index the only way to find "the last 15 minutes" is to read every row:

```
Parallel Seq Scan on requests r  (actual rows=509 loops=3)
  Filter: (received_at >= (now() - '00:15:00'::interval))
  Rows Removed by Filter: 399491          <- per worker: ~1.2M rows read to keep 1,527
  Buffers: shared hit=288 read=13349      <- ~13,600 pages (~106 MB) touched
Execution Time: 19.510 ms
```

With `requests (server_id, received_at)` the planner loops over the 3 servers and, for each, jumps straight to that server's last 15 minutes in the index:

```
Nested Loop
  ->  Index Scan using servers_pkey on servers s          (rows=3)
  ->  Bitmap Heap Scan on requests r                      (rows=483 loops=3)
        ->  Bitmap Index Scan on requests_server_received_idx
              Index Cond: ((server_id = s.id) AND (received_at >= (now() - '00:15:00'::interval)))
Buffers: shared hit=71                    <- 71 pages instead of ~13,600
Execution Time: 0.714 ms
```

In plain words: a B-tree keeps entries sorted by (server_id, received_at), so all of one server's rows sit together in time order and "server 2, after 10:45" is one contiguous slice: find its start (a few page reads down the tree), read until it ends. The query is written to start from `servers` precisely so the planner can use the index once per server. It is "only" 26× here because the whole 1.2M-row table fits in RAM and 2 parallel workers scan it in 19 ms; the gap grows with the table, since the seq scan grows with *all* rows while the index scan grows only with the rows in the window.

**Training export: the latest heartbeat before each request.** Without `server_metrics (server_id, recorded_at)`, the LATERAL subquery has to scan and sort the metrics table once *per request*:

```
Nested Loop Left Join  (rows=100)
  ->  Index Scan Backward using requests_pkey on requests r      (rows=100)
  ->  Limit -> Sort (top-N heapsort)                             (loops=100)
        ->  Seq Scan on server_metrics  (actual rows=691166 loops=100)
              Filter: ((recorded_at <= r.received_at) AND (server_id = r.server_id))
              Rows Removed by Filter: 1382437
Buffers: shared hit=16005 read=1922000    <- ~1.9 million page reads for 100 rows
Execution Time: 13777.920 ms
```

With the index it is one probe per request: go to (this server, this time) in the index and step back one entry, which is the newest heartbeat before the request:

```
Nested Loop Left Join  (rows=100)
  ->  Index Scan Backward using requests_pkey on requests r      (rows=100)
  ->  Limit  (loops=100)
        ->  Index Scan Backward using server_metrics_server_recorded_idx on server_metrics  (rows=1 loops=100)
              Index Cond: ((server_id = r.server_id) AND (recorded_at <= r.received_at))
Buffers: shared hit=405                   <- 4 pages per request
Execution Time: 0.267 ms
```

That turns the full export from impractical into 2.8 s (measured). Without the index it was not run: at the measured ~108 ms per request, 1.19M requests works out to roughly 36 hours (arithmetic, not a measurement; the planner's own cost estimate was 61 billion units).

**What indexes cost.** 36 MB + 62 MB of disk, and every INSERT must also update both B-trees (the insert benchmark ran with both indexes present). Postgres does not create indexes on foreign-key columns by itself; they are added where a query needs them, and the `EXPLAIN ANALYZE` above is how you show they are needed.

## Interview questions this project answers

Short answers, each pointing at the code that backs it. Numbers are measured (see `README.md` and `experiments/results/`).

**1. Why a fixed thread pool with a bounded queue instead of a new thread per connection?**
Thread-per-connection has no upper bound: a traffic spike creates thousands of threads, each with its own stack. With the pool (`lb/server.py`, `lb/bounded_queue.py`) thread count is fixed. When the queue is full the listener stops calling `accept()`, so overload backs up into the kernel's listen backlog (backpressure). Measured: similar throughput up to 200 clients, but 437 threads vs a fixed 257 at 500 clients.

**2. How does your bounded queue avoid busy-waiting and lost wake-ups?**
One mutex and two condition variables, `not_full` and `not_empty` (`lb/bounded_queue.py`). `wait()` atomically releases the mutex and sleeps, so no wake-up can slip in between the check and the sleep. Waiters re-check their condition in a `while` loop, because another thread may take the slot first and wake-ups can be spurious.

**3. What is the readers-writers problem, and where do you use it?**
Per-backend stats (`lb/stats.py`) are read on every routing decision but written only when a request starts or ends. `lb/rwlock.py` lets many readers in together and a writer in alone. It prefers writers: a waiting writer blocks new readers, otherwise a steady stream of readers could starve it forever.

**4. How do you prevent deadlock?**
By breaking circular wait. No code path holds two locks at once. If one ever must, it follows a documented global lock order (`lb/server.py` docstring, the table above). Locks are never held while logging, doing I/O or calling a strategy, because `logging` has its own lock.

**5. How does graceful shutdown work, and why does the signal handler do almost nothing?**
SIGINT/SIGTERM sets a flag. The listener then closes the listening socket, workers finish in-flight and queued requests (up to `shutdown_timeout`), and the DB writer flushes its queue last. The handler runs on the main thread between bytecodes, so taking any lock there (even logging's) could deadlock against the code it interrupted.

**6. TCP is a byte stream. How do you know where an HTTP request ends?**
Read until the blank line `\r\n\r\n` that ends the headers, then exactly `Content-Length` bytes (or decode chunked encoding) (`lb/http_parser.py`, `SocketReader`). One `recv()` can return half a request or two, so leftover bytes stay buffered. Ambiguous framing (two different Content-Lengths, or both Transfer-Encoding and Content-Length) is rejected because it enables request smuggling.

**7. 502 vs 503 vs 504?**
502 Bad Gateway: the backend refused, reset or sent garbage. 503 Service Unavailable: no backend was available at all. 504 Gateway Timeout: the backend didn't connect or answer in time (`lb/proxy.py`, `_attempt`). Keeping them distinct tells an operator whether a backend is broken, missing, or slow.

**8. Why are only GET and HEAD retried?**
Retrying is only safe for idempotent requests. A POST whose connection broke may already have been processed, and resending it could act twice. Retries go to a different backend with exponential backoff, at most 2 (`lb/proxy.py`), and only when there was no usable answer: a 500 is passed through, not retried.

**9. Health checks and a circuit breaker: isn't that redundant?**
No. Health checks (`lb/health.py`) are active: synthetic TCP + `GET /health` probes every 2 s, needing 2 failures to mark a backend down and 2 passes to bring it back. They notice a dead backend that gets no traffic and confirm recovery. The breaker (`lb/circuit_breaker.py`) is passive: 5 consecutive real failures open it at once, and after a 5 s cooldown a few half-open trial requests decide whether to close it.

**10. Why UDP for heartbeats?**
A heartbeat is a "latest value" report every second, so a lost one is simply replaced by the next. TCP's retransmission and ordering would only delay fresh data behind stale data. UDP can reorder and duplicate datagrams, so each carries `(agent start time, sequence number)` and older ones are dropped (`lb/heartbeat.py`).

**11. What does connection pooling save, and how do you avoid reusing a dead connection?**
It saves the TCP three-way handshake per request and the TIME_WAIT socket each close leaves behind. Measured: +29–35% throughput and 0.5 instead of 1,000 backend handshakes per 1,000 requests. Before reusing an idle connection, a non-blocking `recv(1, MSG_PEEK)` checks whether the backend has closed it (`lb/connection_pool.py`). If the backend closes it just as it is reused, idempotent requests get one retry on a fresh connection.

**12. How does the token-bucket rate limiter work, and why no timer thread?**
Each client IP has a bucket of `burst` tokens refilled at `rate` per second. A request takes one token; an empty bucket means 429 with `Retry-After` (`lb/rate_limiter.py`). Refill is lazy: on each check, `min(burst, tokens + elapsed × rate)`. That costs O(1) and needs no thread. The check-and-decrement happens under a lock so two threads can't spend the same token.

**13. Why one database writer thread instead of each worker inserting its row?**
A per-request insert puts a network round trip and a commit (fsync) on the request path and makes 32 connections contend. Workers instead do a non-blocking `put()`, and one writer inserts batches of up to 200 rows per transaction (`lb/db_writer.py`): 52,512 vs 3,060 rows/s. A database outage only fills the queue. When it is full, records are dropped and counted rather than blocking clients.

**14. What did your indexes change, and why that column order?**
`requests(server_id, received_at)`: equality column first, range column second, so "server X in the last 15 minutes" is one contiguous slice of the B-tree. With `EXPLAIN ANALYZE` on 1.2M rows the dashboard queries went from 19–34 ms to under 1 ms. The `LATERAL` "latest heartbeat before each request" lookup went from 10.8 s to 0.27 ms for 100 requests: one index probe instead of a scan per row.

**15. How do you compute p95 latency, and why p95 rather than the average?**
In SQL, with `percentile_cont(0.95) WITHIN GROUP (ORDER BY response_time_ms)` (`db/queries.sql`, `RUN_RESULTS_SQL`). The average hides the tail: in the sudden-slowdown scenario least connections' average was *above* its p95, because a few 300 ms answers raised the average while staying in the slowest 5%. Users feel the tail, so the comparison leads with p95.

**16. How did you make the experiments fair and repeatable?**
Each run starts fresh backend processes and a fresh LB, so no state carries over. Every strategy gets the same seeds, so it sees the identical sequence of arrivals. The load generator is open-loop (it sends on schedule even when the server is slow, avoiding coordinated omission). Every cell is repeated 5 times and reported as mean ± SD. The results are computed in SQL and cross-checked against the client's own count on every run.

**17. Why split the ML data by time and not randomly?**
Consecutive requests are almost identical (same backend state a few milliseconds apart), so a random split puts near-copies of each test row in training, and the model gets credit for memorising them. `ml/train.py` trains on the first 70% of each run and tests on the last 30%, the way the model is used live: on a future it has never seen. Measured: a random split scored the random forest at 6.8 ms MAE, the time split at 80.5 ms.

**18. Linear regression beat the random forest. Why?**
Part of the test period was round robin's growing backlog, with response times up to 7.6 s, beyond anything in training (3.5 s). A tree can only predict values it has seen, while a line extrapolates. For normal requests (under 200 ms), no model beat simply predicting the recent average. The unlimited-depth tree reached 0.0 ms training MAE and 80.5 ms test MAE: textbook overfitting.

**19. Exploration vs exploitation: how does your bandit balance them?**
Epsilon-greedy (`lb/strategies/bandit.py`). With probability ε = 0.1 it picks a random healthy backend (explore); otherwise it picks the one with the best mean reward, where reward = −latency over that backend's last 50 requests (exploit). The sliding window forgets old rewards, so it notices a backend that slows down. The measured cost of exploring: it keeps sending a few percent to slow backends, which shows up in its p95.

**20. What happens if the ML model breaks, and is it worth its cost?**
Both ML strategies run inside `GuardedStrategy` (`lb/strategies/guarded.py`). A missing model, an unknown feature, an exception, NaN output or a decision over 2 ms means least connections decides that request, and a counted warning is logged. A decision costs ~34 µs vs ~4 µs for least connections. It pays off only where backends differ in speed, and the win comes from routing on latency, not from the model's accuracy (see the README's results section).
